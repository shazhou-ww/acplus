## 为什么采用空闲退出

目标是让脚本和日常 acplus
CLI 使用无需显式启动、维护后台服务，不是移除 HTTP 服务或改为每个命令独立执行 Agent。

Session 是可持续追加 Turn 的历史容器；一次 Turn 完成不代表整个 Session 完成。因此采用“无执行工作且经过空闲宽限期后退出”，不采用“Session 全部跑完就退出”。当前构想不新增 sessions
close 或完整流程 run 命令。

## 操作分流

以下为无显式 URL 的本地模式目标；显式 `--url` 或 `ACPLUS_URL`
仍只连接指定服务，即使目标是 loopback，也不隐式启动或替换它。

| 操作              | 目标行为                           | 重要边界                                                   |
| ----------------- | ---------------------------------- | ---------------------------------------------------------- |
| sessions list/get | 直接读取已提交历史                 | 不启动 server 或 Agent                                     |
| turns list/get    | 直接读取已提交历史                 | 返回最后持久化的状态，而非进程存活证明                     |
| events list       | 直接读取已提交事件                 | 保持 Session-wide sequence、turnId 过滤和分页语义          |
| sessions create   | 按需启动或复用本地服务，创建元数据 | 创建本身仍不启动 Agent；保留后续 start 的空闲宽限期        |
| turns start       | 按需启动或复用本地服务执行         | 执行期间服务保持存活                                       |
| turns cancel      | 定位持有该工作的真实服务并请求取消 | 新起进程不能代替原进程证明取消；缺失或结果不明必须显式报告 |
| 显式 serve        | 常驻 HTTP 服务                     | 不因自动模式的空闲策略退出                                 |

现有接口不是每个资源都有 create：执行对应 turns
start，事件由执行产生，不增加 events create。

agents
list/auth 包含运行状态、能力或当前登录流程，不能统一改成离线持久化查询。认证历史观测可与实时信息区分，但其新的 CLI 路由不属于本构想承诺。health 仍表示服务健康，数据库可读不能替代它。

## 历史读取不接管执行

- 只读路径不创建数据库、迁移 schema、修改权限、恢复任务或接管写者锁。缺失、损坏、版本不兼容和访问失败均须显式报错，不能返回伪造的空历史。
- server 停止或 Agent 不可用时，已提交历史仍可读取。server 正在写入时，读取应看到一致的已提交快照；不同命令或分页请求之间不承诺同一冻结快照。
- 持久化的 running/cancelling 可能是停止前最后一次观测；离线读既不能声称工作仍活跃，也不能把它擅自改为完成、失败或取消。
- 本地历史查询不经过 server，因此不应成为维持后台执行服务常驻的必要条件。

## 自动服务的生命周期边界

- 同一数据目录复用一个写者服务，多个 Session 共享它；不采用每 Session 独立 server，避免违反现有数据目录所有权。
- 连续命令与并发首次调用必须可靠衔接。服务发现或启动失败不能降级为另一写者，也不能仅凭端口或 PID 假定找到了正确服务。
- 只有自动启动的服务启用空闲退出。执行、登录流程和其他在途操作不能被空闲退出打断；退出与新请求竞争不能丢失已接纳的工作。
- 正常退出须先提交事件与终态，再关闭 Agent、释放所有权。意外退出不能被当成执行完成或取消的证据；结果不明仍遵守 unknown 的对账与不自动重放约束。
- 服务再启动不等于 Agent 上下文已恢复。后续 Turn 仅使用 Agent 已支持的 resume/load；不支持时显式处理，不能静默重放历史来伪造恢复。

## 留待实施阶段确定

空闲宽限期的具体值与是否开放配置、进程发现和启动握手的机制、退出竞争的请求响应方式，以及可支持平台的后台进程管理方式，留待实施契约细化并用进程测试证明。上述机制不得削弱本页已说明的历史、所有权及执行真实性边界。
